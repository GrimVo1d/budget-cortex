# Architecture

## Overview

```
client ──HTTP──> api (gunicorn + Django/DRF) ──> PostgreSQL 16
                    │                              ▲
                    ├──> Redis db 0: cache (FX rates, throttling)
                    └──> Redis db 1: Celery broker ──> worker ─┘
                                                      ▲
                                    beat (schedule) ──┘
```

One Django project (`src/budget_cortex/`) with a settings package (`base`, `dev`,
`prod`, `test`), one Celery app, and a set of Django apps under `src/apps/`. Celery
tasks live in `src/tasks/`. The same image runs every role; the entrypoint argument picks
`api`, `worker`, `beat` or `migrate`.

All API routes are under `/api/v1/`. The OpenAPI schema is generated by drf-spectacular
(`/api/schema/`, Swagger UI at `/api/schema/swagger-ui/`), and a test keeps it free of
generator warnings. `/health/live` and `/health/ready` (database and cache) are
unauthenticated and excluded from the schema.

## Apps

| App | Responsibility |
|-----|----------------|
| `core` | `AuditLog` model and signal receivers, audit actor binding, `UserScopedModelViewSet`, owner-restricted serializer fields, error handler, CSV streaming, health views, JSON log formatter |
| `accounts` | `Account`; registration, JWT token, refresh and logout endpoints |
| `ledger` | `Category` (two levels), `Tag`, `Transaction`; transfer service, running balance in the list, CSV export |
| `budgets` | `Budget`, live `/budgets/{id}/status/` |
| `analytics` | Materialized-view migrations, raw-SQL reports, `refresh_views` command |
| `fx` | `FxRate`, `get_rate()` with cache → database → provider lookup, stub provider |
| `imports` | `CsvImport` job, upload endpoint, file storage, bank CSV parsers (app label `imports_app`) |

## Data model

```
User ─┬─< Account ─────────────< Transaction >──┬── Category (parent → Category)
      ├─< Category                    │         └──< Tag (many-to-many)
      ├─< Tag                         └── transfer_pair → Transaction
      ├─< Budget ── Category (optional)
      └─< CsvImport ── Account
FxRate (base, quote, effective_on)          AuditLog (actor → User)
```

- Money is `NUMERIC(14, 2)` everywhere, FX rates `NUMERIC(20, 10)`; Python uses
  `Decimal` end to end and the API serializes decimals as strings
  ([ADR-0001](ADR/0001-decimal-for-money.md)).
- `Transaction.amount` is signed: negative is an outflow. `type` is `regular`,
  `adjustment` or `transfer`; transfer legs are created only by the transfer service and
  point at each other through `transfer_pair`.
- `Category.kind` (`income` or `expense`) decides how a categorized transaction counts in
  reports. Categories nest one level deep: a child's parent must be a root, and a category
  with children cannot become a child. Names are unique per level among live rows, and a
  category with live children cannot be deleted (`409 category_has_children`).
- Accounts, categories, tags, transactions and budgets have `is_deleted` / `deleted_at`.
  The API never issues SQL `DELETE` for them; deleting a transfer leg soft-deletes both legs
  ([ADR-0003](ADR/0003-soft-delete-and-audit.md)).
- `Budget` covers the half-open range `[period_start, period_end)` in one currency, for one
  category (children included) or for all categories when `category` is null
  ([ADR-0005](ADR/0005-budget-period-range.md)).
- A transaction is always in its account's currency: the API and the CSV import reject
  anything else, and an account's currency is fixed once it has transactions (deleted
  ones included). So the running balance can sum amounts as they are. Rows written before
  this rule are not rewritten; editing their account or currency has to fix the mismatch. Money moves between
  currencies only through a transfer. Reports group by currency instead of
  converting ([ADR-0004](ADR/0004-multi-currency-normalization.md)).

## Request handling

- **Authentication.** simplejwt, HS256 with its own signing key. Access tokens live
  15 minutes, refresh tokens 7 days; refreshing rotates the pair and blacklists the old
  refresh token, and `auth/logout/` blacklists one explicitly. Passwords are hashed with
  Argon2 and checked by Django's password validators.
- **Tenant isolation.** `UserScopedModelViewSet` filters every queryset by
  `user_id = request.user` and `is_deleted = false`, so another user's id is a plain 404.
  Foreign keys in request bodies and query filters (`account`, `category`, `parent`, `tags`,
  transfer accounts) go through `OwnedPrimaryKeyRelatedField` / `owned()` querysets, so a
  foreign or deleted id fails exactly like a non-existent one. The one exception is an
  update that keeps the value already stored: a transaction whose category was deleted
  later can still be edited without re-picking it. Raw SQL reports always take the user id
  as a bound parameter.
- **Errors.** One exception handler turns every error into
  `{"code": "...", "detail": ...}`. Codes include `validation_error`, `not_found`,
  `not_authenticated`, `token_not_valid`, `throttled`, `invalid_month`, `invalid_range`,
  `transfer_error`, `category_has_children`, `duplicate_file`, `file_too_large`,
  `report_not_ready`, `queue_unavailable`. Database errors that slip past validation never
  become an HTML 500: `IntegrityError` is `409 conflict`, `DataError` is `400 invalid_value`.
- **Ordering.** List endpoints accept `ordering`, and the id is always appended as the last
  key in the same direction, so rows with equal timestamps have a stable order across
  pages.
- **Throttling.** Anonymous 60/min, authenticated 600/min, and a separate `auth` scope of
  10/min on register, token, refresh and logout. Counters live in the Redis cache and are
  keyed by the client address. `X-Forwarded-For` is ignored unless `NUM_PROXIES` says how
  many trusted proxies sit in front of the API.
- **Audit actor.** `AuditActorMixin.initial()` binds the DRF-authenticated user to a
  `ContextVar` after authentication; `AuditMiddleware` resets it per request. Celery
  tasks set it explicitly (CSV import rows are attributed to the job owner).

## PostgreSQL techniques

PostgreSQL-only DDL goes through `RunPython` operations that check
`schema_editor.connection.vendor == "postgresql"`, so one migration chain applies to both
PostgreSQL and the SQLite test database. Tests that need these objects are marked
`requires_postgres` and run with `make test-pg`.

### Running balance: window function

`apps/analytics/queries/running_balance.py`

```sql
SUM(amount) OVER (PARTITION BY account_id ORDER BY occurred_at, id
                  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
```

The window runs over the user's whole live ledger and is then narrowed to the ids on the
current page, so the value does not depend on pagination or filters. The list endpoint
adds the account's `opening_balance`. The query also runs on SQLite (3.25+), where the
sum comes back as a float and is quantized back to cents.

### Materialized views

`apps/analytics/migrations/0001_materialized_views.py`, `0002_cashflow_uncategorized.py`
([ADR-0002](ADR/0002-materialized-views.md))

| View | Key | Columns | Source rows |
|------|-----|---------|-------------|
| `mv_monthly_category_totals` | `(user_id, category_id, month, currency)` | `total_expense`, `tx_count` | live transactions in `expense` categories |
| `mv_monthly_cashflow` | `(user_id, month, currency)` | `income`, `expense`, `net` | live non-transfer transactions; category kind decides, uncategorized rows go by the sign of the amount |

Both views are created `WITH NO DATA` and carry a unique index on their key, which
`REFRESH MATERIALIZED VIEW CONCURRENTLY` requires. The refresh task checks
`pg_class.relispopulated`: an empty view gets a plain `REFRESH` first, after that the
refresh is concurrent so report reads are never blocked. If a concurrent refresh fails,
the task logs it and falls back to a blocking refresh. Until the first refresh after
`migrate` the views are not populated, and the report endpoints answer
`503 report_not_ready`.

### Reports

| Endpoint | Query | Technique |
|----------|-------|-----------|
| `GET /reports/cashflow/?from=YYYY-MM&to=YYYY-MM` | `queries/cashflow.py` | range scan on `mv_monthly_cashflow` |
| `GET /reports/by-category/?from=…&to=…` | `queries/by_category.py` | recursive CTE maps every category to its root, joined with `mv_monthly_category_totals` |
| `GET /reports/overruns/` | `queries/overruns.py` | budgets joined with the category MV; a budget counts its own category and its children |

Month ranges are half-open (`to` is the month after the last one). The by-category CTE:

```sql
WITH RECURSIVE roots(id, root_id) AS (
    SELECT c.id, c.id FROM ledger_category c
    WHERE c.parent_id IS NULL AND c.user_id = %(user_id)s
  UNION ALL
    SELECT c.id, r.root_id FROM ledger_category c
    JOIN roots r ON c.parent_id = r.id
    WHERE c.user_id = %(user_id)s
)
```

The overruns report works at month granularity: every month that overlaps a budget
period counts in full, so it is exact for month-aligned budgets. `/budgets/{id}/status/`
is the precise, live per-budget view: it aggregates transactions with the ORM straight
from `ledger_transaction`.

### Indexes and constraints

| Object | Kind | Purpose |
|--------|------|---------|
| `tx_user_occurred_alive_idx`, `tx_account_occurred_alive_idx`, `tx_category_alive_idx`, `account_user_alive_idx`, … | partial B-tree `WHERE NOT is_deleted` | hot paths only index live rows |
| `tx_user_import_hash_unique` | partial unique `(user_id, import_hash) WHERE import_hash IS NOT NULL` | idempotent CSV import without indexing manual rows |
| `tx_external_id_idx` | partial `WHERE external_id IS NOT NULL` | lookups by external id |
| `tx_occurred_at_brin` | BRIN on `occurred_at` (PostgreSQL only) | cheap index for historical range scans on an append-mostly table |
| `budget_no_overlap` | GiST exclusion constraint (PostgreSQL only, `btree_gist`) | no two live budgets of one user, category and currency overlap |
| `budget_period_range_idx` | partial B-tree | portable range scans on budget periods |
| `category_unique_alive_per_parent`, `category_unique_alive_root`, `tag_unique_alive_per_user` | partial unique | names unique among live rows only; root categories need their own constraint because `NULL` parents never compare equal |
| `mv_*_uniq` | unique on each MV | required for concurrent refresh |
| `auditlog_append_only` | `BEFORE UPDATE OR DELETE` row trigger (PostgreSQL only), function with a pinned `search_path` | audit rows cannot be changed or removed; `actor` is `PROTECT`, so a user who appears in the log is deactivated rather than deleted |

The exclusion constraint:

```sql
EXCLUDE USING gist (
    user_id WITH =, (COALESCE(category_id, 0)) WITH =, currency WITH =,
    tstzrange(period_start, period_end, '[)') WITH &&
) WHERE (NOT is_deleted)
```

The budget serializer runs the same overlap check portably, so clients get a clean 400
and SQLite behaves the same; the constraint is the guarantee under concurrency.

## Background jobs

Celery with Redis as broker and result backend. Task modules are listed explicitly in
`CELERY_IMPORTS`. Logging stays under Django's `LOGGING` (Celery does not hijack the root
logger), so worker logs have the same format as the API.

| Task | Queue | Schedule (UTC) | What it does |
|------|-------|----------------|--------------|
| `tasks.imports.parse_csv_import` | `default` | on upload | parses a stored file, inserts rows, marks the job `done` or `failed` |
| `tasks.analytics.refresh_materialized_views` | `low` | hourly, minute 0 | refreshes both MVs (retries with backoff) |
| `tasks.fx.fetch_fx_rates` | `low` | daily 06:00 | stores today's rate to `FX_BASE_CURRENCY` for every currency in use |
| `tasks.imports.cleanup_csv_files` | `low` | Sundays 03:00 | deletes stored files of finished imports older than 30 days; fails jobs stuck in `pending` for over 24 hours |
| `tasks.auth.flush_expired_tokens` | `low` | daily 04:00 | drops expired refresh tokens from the blacklist tables |

The worker consumes both queues by default (`entrypoint.sh worker default,low`); they can
be split across workers. `manage.py refresh_views` runs the refresh synchronously.

### CSV import pipeline

1. `POST /imports/` (multipart: `account`, `fmt`, `file`). The view refuses a request
   whose `Content-Length` already exceeds `IMPORT_MAX_BYTES` before reading the body, then
   rejects files over the limit (413) and files whose SHA-256 the user already uploaded
   (409). It stores the file as `MEDIA_ROOT/imports/<user_id>/<uuid>.csv` and creates a
   `pending` job. The client's file name is never used. Uploading a file whose earlier
   job `failed` retries that job instead of answering 409.
2. After the transaction commits, `parse_csv_import` is queued and the view answers 202.
   If the broker is down, the job is marked `failed`, its file is removed and the view
   answers `503 queue_unavailable`; the same file can be uploaded again later.
3. The worker re-checks that the account belongs to the job owner and is live, resolves
   the stored path (refusing anything outside the imports directory), parses the file
   with the format's parser and inserts all rows in one transaction with
   `get_or_create` on `(user, import_hash)`.
4. `import_hash` is the SHA-256 of a line's cells; repeated identical lines in one file
   get an occurrence suffix. Re-importing an overlapping statement inserts only new lines.
5. Any parse or database error marks the job `failed` with a short message; nothing
   stays in `parsing`.

### FX rates

`apps.fx.services.get_rate(base, quote, on)` returns the rate for one day: Django cache
(24 h) → `fx_fxrate` table → configured provider (the result is stored and cached).
A cache outage degrades to database lookups. `stub` is the only shipped provider; it
returns fixed rates and is meant for development. Transfers between currencies take the
rate from the client and store the converted amount on the credit leg.

## Security

### Controls

| Area | Threat | Control |
|------|--------|---------|
| Authentication | stolen or replayed tokens | 15-minute access tokens, rotating refresh tokens with blacklist, logout; JWT key separate from `SECRET_KEY` |
| Authentication | password guessing | Argon2, Django password validators, `auth` throttle of 10/min |
| Authorization | IDOR across users | user-scoped querysets, owner-restricted related fields and filters, 404 instead of 403 |
| Authorization | references to deleted rows | owner-restricted querysets exclude soft-deleted rows |
| Injection | SQL injection in raw reports | all values are bound parameters; the only text formatted into SQL is `%s` placeholder lists and view names from a constant tuple |
| Injection | spreadsheet formula injection via export | text cells starting with `= + - @`, tab, CR or LF, also after leading spaces, are prefixed with `'` |
| Uploads | path traversal, oversized files | server-generated names, path confinement in the worker, size limit checked before the body is read, per-user dedup by hash |
| Availability | throttle bypass | client address taken from the socket; `X-Forwarded-For` trusted only for `NUM_PROXIES` hops |
| Integrity | silent edits | audit log with before/after snapshots and actor for accounts, categories, transactions and budgets, append-only through a database trigger; transfer legs cannot be edited |
| Integrity | half-written transfers | both legs in one database transaction; cross-currency transfers require a positive rate |
| Configuration | default or missing secrets in production | `settings.prod` refuses short, `dev-insecure*` or shared keys and a missing `ALLOWED_HOSTS`, `DATABASE_URL`, `REDIS_URL` or Celery URL |
| Information disclosure | API surface mapping | in `prod` the OpenAPI schema and Swagger UI are served to staff users only; Swagger UI assets are pinned to one version; JSON logs carry the request path without the query string |
| Transport | downgrade, cookie theft | SSL redirect (health endpoints exempt), HSTS, secure cookies, `X-Frame-Options: DENY`, nosniff |
| Infrastructure | exposed services, container escape | ports bound to 127.0.0.1, Redis password, no Redis port published; containers run as uid 1000 under `tini` with all capabilities dropped and `no-new-privileges` |
| Supply chain | tampered dependencies, leaked secrets | hash-pinned `requirements/*.txt` (`pip --require-hashes`), no pip in the runtime image, gitleaks in pre-commit from a pinned image |

### Accepted risks

- The append-only trigger stops accidental rewrites (a stray ORM `update()` or `delete()`),
  not a compromised application: the application role owns the table, so with SQL
  injection or code execution it could `TRUNCATE` it (test teardown does) or drop the
  trigger. Inserts are not restricted either, so append-only does not prove that a row is
  genuine. `QuerySet.update()` and `bulk_create()` bypass signals, so they would skip the
  log; the code does not use them on audited models.
- The application connects to PostgreSQL as the database owner; a separate low-privilege
  role would need an init script.
- Registration reveals whether a username exists (unavoidable with open sign-up); the auth
  throttle limits enumeration.
- `/admin/` has no brute-force lockout beyond Django's defaults, and its static files are
  not served under gunicorn. The API does not depend on it.
- Container images use version tags rather than digests; Python dependencies are pinned
  by hash. Rebuild with `--pull` to pick up base-image security fixes.
- `/health/ready` is public and says whether the database and Redis answer; it reveals
  nothing else, and orchestrators need it unauthenticated.
- The Redis password is passed as an environment variable, so `docker inspect` shows it to
  anyone with access to the Docker socket.
- Transaction descriptions are stored in plain text; encryption at rest is left to the
  database host.

## Known limitations

- Reports and budgets are per currency; nothing converts amounts between currencies.
- Report data can be up to an hour old (refresh schedule); budget status is live.
- Budgets and the category MV only see categorized transactions of `expense` kind, so
  imported rows count toward budgets once they are categorized.
- Currency codes are checked for shape (three uppercase letters), not against ISO 4217.
- The audit log has no API; read it from the database or the Django shell.
